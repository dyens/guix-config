# Ревью ветки через git, без GitLab API

Ветка читается **локально из git**. Никакого `glab`, никакого GitLab API — ни на чтение,
ни на запись. Имя ветки приходит аргументом или из сообщения; ведущий `origin/` отбросить.
База по умолчанию — `develop`.

Если ветка не названа — спросить и остановиться. Не подменять её текущим рабочим деревом.

## 1. Фетч

Автор ребейзит и force-пушит в свою ветку (`docs_flow/pravila-raboty-s-git.md`, §6),
поэтому фетч всегда с `-f` в стабильный tracking-ref:

```bash
git fetch -f origin "<branch>:refs/remotes/origin/<branch>"
git fetch origin develop
SHA=$(git rev-parse "origin/<branch>")
BASE=$(git merge-base origin/develop "origin/<branch>")
```

`$SHA` — якорь ревью. Он обязан попасть в команду для автора дословно. Никогда не описывать
якорь как «последний коммит»: после ребейза это разные вещи.

## 2. Читать изменение, а не дифф

```bash
git log --oneline --no-merges "$BASE..origin/<branch>"
git diff --stat "$BASE...origin/<branch>"
git diff "$BASE...origin/<branch>"          # три точки = от merge-base
```

Код лежит на диске — в этом весь смысл локального флоу. Открывать целые файлы, которые
задел дифф, и вызывающих/вызываемых вокруг. Сверять с конвенциями `CLAUDE.md`: Querier-шов
`s.q(ctx)` в стораджах, тенант-скоуп чтений через `queryTenant`/`appendTenantFilter`,
реестр настроек вместо config.json, `pnpm` не npm, `uv` не pip, Tailwind/HeroUI/zustand
запрещены в `ui/user-front/`, сгенерированный sqlc в `internal/credbroker` не правится
руками. Искать тесты на изменение — и тесты, которые должны были измениться, но не изменились.

## 3. Быстрые локальные проверки

Тег `goolm` обязателен для любой go-команды:

```bash
export GOFLAGS=-tags=goolm
go build ./... && go vet ./<изменённые пакеты>
go test ./<изменённые пакеты>/...        # только unit
scripts/ci/check-commit-message.sh       # формат type(TICKET): summary
scripts/ci/check-changelog.sh            # трейлеры Changelog/ChangelogMessage
```

Никогда: `make test-wiring`, что-либо под `RUCLAW_TEST_INTEGRATION`, `make up*`, docker build.
Отчитаться, что запускалось и с каким результатом. Что пропустил — сказать прямо.

## 4. Показать ревью в чате

Notes на этом шаге **не писать**. Напечатать и остановиться:

```markdown
## Review: <branch> @ <short-sha>
База: develop (merge-base <short-base>) · <N> коммитов · <N> файлов, +<A>/-<D>

## Блокирующее
- **[blocker]** `file:line` — что не так, чем сломается, что сделать вместо

## Надо поправить
- **[major]** / **[minor]** `file:line` — ...

## Мелочи
- `file:line` — ...

## Тесты
<что покрыто, чего не хватает>

## Локальные проверки
<команда → результат>
```

`file:line` обязательны везде: git note не умеет привязываться к строке диффа, ссылка —
единственный способ для автора найти место. Сортировать по серьёзности. Если блокирующего
нет — сказать это прямо, не добивать список мелочами.

Затем сообщить: ревью пока не сохранено, скажи «сохрани» — запишу в notes.

## 5. Сохранить — ТОЛЬКО по явной просьбе

Никогда не делать этот шаг самостоятельно и никогда вместе с шагом 4.

Записать тело ревью (markdown из шага 4, **без** заголовка раунда — его добавит скрипт)
в файл в scratchpad и вызвать:

```bash
.claude/skills/review-branch/scripts/save-review-note.sh "$SHA" <scratch>/review.md
```

Скрипт сам синхронизирует notes-ref, посчитает номер раунда, допишет через `append`
(прошлые раунды сохраняются), запушит и напечатает блок для автора. Руками
`git notes remove`, `add -f` и force-push notes-ref не делать никогда.

Границы шага: трогать только `refs/notes/review`. Не коммитить, не пушить ветки, не пушить
в `develop`, не амендить и не ребейзить ветку автора.

## 6. Отдать автору

Передать пользователю блок, который напечатал скрипт, как есть — он форвардит коллеге.
И напомнить, чего этот флоу не делает: нет треда, нет резолва замечаний, нет уведомления
автору и нет следа в MR о том, что ревью было. Approve и мерж по-прежнему через GitLab.
