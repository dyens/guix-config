# Простой последовательный runner без LLM

Runner только выбирает доступную задачу, открывает свежий Pi в tmux и ждёт его
сигнала. Исполнитель сам делает implement → tests → independent review → fixes →
non-force push → task done → cleanup своих временных ресурсов. Runner **не принимает
работу**, не читает отчёты и не разрешает спорные вопросы.

## Попробовать

После `homerec` и открытия нового shell, внутри tmux (из любого cwd):

```sh
pi-ruclaw-runner .scratch/RCL-821 --only 08,09
```

Без активации Guix Home — тот же запуск из исходников:

```sh
python3 ~/vms/guix-config/files/pi-ruclaw/runner/run.py .scratch/RCL-821 --only 08,09
```

Без `--only` — все существующие незавершённые задачи тикета в основном checkout
`~/dev/croc/ruclaw`. Для smoke лучше одна-две задачи.
Runner использует `launch.py`, `profile/`, `agents/` и `skills/` из своего корня
`pi-ruclaw`. Для запуска через Python `homerec` не требуется.

Один раз подтверди scope, обычные commits/non-force push и укажи дополнительные
ограничения/ресурсы. По умолчанию разрешён локальный Docker/Compose для изолированных
стендов и зависимостей своей задачи/тикета: build/pull образов, создание, запуск,
перезапуск, остановка и удаление контейнеров и их собственных сетей. Перед изменением
существующих ресурсов нужно проверить ownership/isolation. Это разрешение может
получить ops-subagent в тех же границах; повторно спрашивать о каждом up/stop/rm не нужно.
Чужие/shared/production ресурсы, global prune, удаление volumes или сброс persistent-данных —
только с отдельным разрешением. Явные ограничения пользователя имеют приоритет.
Прочие внешние/опасные действия автоматически не разрешаются. Не вставляй секреты
или историю. Для уже сделанной 08 полезно указать текущий
`.scratch/RCL-821/08-checkpoint.md`: исполнитель сначала сверяет существующую работу.
Перед запуском останови других писателей в этом checkout.

- Каждая задача получает **новый процесс и сессию Pi**, без прошлой переписки.
- Первый pane появляется справа от runner; следующие — под предыдущим в правой
  колонке. Если предыдущий pane закрыт, используется последний оставшийся pane
  этой колонки; если закрыты все — снова split справа от runner.
- В новом pane вызывается `/skill:implement` для одной задачи.
- Внутри задачи используется default plan-cycle v2: intake → `plan_cycle_start`
  → короткий последовательный план → шаги через `plan_cycle_next` → проверки и
  финальный fresh `ruclaw-plan-reviewer`. Findings становятся новым планом исправлений.
  План/инвалидизация чтений заморожены внутри шага для prefix cache. Publication,
  task status и cleanup остаются обязательными согласованными gates runner.
  Переход шага не завершает job и не освобождает блокировку; только окончательный
  `runner_finish` делает это. Старые фазовые manifests/ruclaw_next_cycle не используются.
- Для переходов используются только Status/Blocked by и сигнал исполнителя.
  Новые задачи, добавленные уже после запуска, автоматически не включаются.
- `runner_finish({status:"done",summary:"…"})` — декларация исполнителя. Никаких
  receipts, SHA/evidence-схем и проверок правильности со стороны launcher.
- После `done` и завершения текущего хода освобождается рабочая блокировка и
  стартует следующая задача. **Pi и pane остаются открытыми**, завершённый агент idle.
  Не запускай изменения из старых pane, пока следующий исполнитель работает в том
  же checkout. Чтение/просмотр истории доступно; runner не закрывает Pi или pane.
- `blocked`/`failed` останавливает runner, но Pi остаётся открытым: обсуждай вопрос
  непосредственно с исполнителем в его pane. После завершения работы можно снова
  запустить runner; он прочитает актуальные task statuses. Повторной реализации
  только ради launcher не требуется.
- Аварийный выход Pi или закрытие pane без завершения останавливает запуск следующих
  задач. Автоматических повторов нет.
- Когда для очередного split не хватает места, создаётся новое tmux-window. Все прежние
  pane сохраняются. Runner печатает ID pane каждой задачи.

## Остановка и ограничения

Ctrl-C останавливает **только runner**, не исполнителя. Сначала закончи/останови
исполнителя в его pane, затем запускай runner заново. Kernel flock защищает от двух
runner и от двух активных runner-задач в одном Git repo (после done
блокировка снимается, хотя Pi остаётся открыт); stale-lock удаления
не нужны. Это не защита от ручного shell или Claude.

При исчезнувших задачах, незавершённых зависимостях или ready-for-human runner
останавливается, а не пытается решать проблему. После изменения требований обычный
исполнитель общается с пользователем и ведёт task source сам; launcher не согласует
требования и не привязывает завершение к прежней сессии.

В `.scratch/RCL-XXX/runner/<run>/<task>/` только `job.json` и два технических сигнала:
`finish.json` от Pi после settled turn и `result.json` после освобождения рабочей
блокировки (или выхода Pi без успешного завершения).
Это не база приёмки и не обязательные отчёты. Достоверность done — ответственность исполнителя,
его независимого review и проверок, как при обычном `/skill:implement`.

## Проверки без LLM

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s files/pi-ruclaw/runner/tests -p 'test_*.py'
node --import ./files/pi-ruclaw/tests/peers.mjs \
  --test files/pi-ruclaw/runner/tests/*.test.ts
```

Тесты не запускают реальные модели и не меняют RuClaw. Tmux-smoke использует отдельный
временный server/socket и stub вместо Pi; production tmux-сессии не затрагиваются.
