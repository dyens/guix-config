# RuClaw Lite — experimental profile

The builder works continuously in this linked experiment worktree. No compulsory
context resets, phase manifests, per-finding sessions or automatic review/fix loops.
Native Pi compaction/settings stay unchanged. Existing system/personal safeguards
apply. Shared project.md is domain orientation; areas/testing are selective lookups.

Read PI_RUCLAW_LAB_RUN once for the actual initial checkout/branch/head. For a prepared
comparison read .scratch/pi-lite/comparison.json and its frozen request. Keep frozen
input files unchanged; record fixes/dispositions in a separate result index. Never use
main-checkout fixes, sibling experiments, prior attempt sessions, completed
solutions or lab/evaluations as a solution oracle. Read only assigned frozen task
inputs and this run's own outputs; historical evaluation artifacts are holdouts.
A worktree isolates files, NOT Docker, network, databases, credentials or Git refs.
Before tests check source/workspace resolution (including Go GOMOD/GOWORK) points
to this worktree, not an absolute path inherited from the primary environment.

Use lite-spec for unresolved requirements; approved specs/external findings need no
rewrite. Use lite-implement for implementation/fixes. The scope is the approved
change, not a fresh audit of every historical feature. Preserve CONTEXT.md domain
terms, real core wiring, tenant/security boundaries and uncertainty/error semantics.
No decorative DDD migrations or unrelated cleanup. Raise real spec conflicts.

Only the main agent edits product code. BEFORE implementation /lite-acceptance
runs the same independent evaluator on the original base to prepare cases and
baseline evidence. Parent checks approved IDs/boundaries/positive-negative controls,
then seals the agreed suite and records its original anchor before source edits.
Builder does not rewrite these assertions/tiers. Permission/scope/test amendments
need an explicit decision and a new seal, preserving prior evidence; not quiet edits.

Finish related fixes/regressions as a batch. Then source review and replay of the
frozen acceptance suite run together; do not formally re-review each finding.
Critical changes focus both roles, not a third pass. No new evaluator role or reset
is introduced: preparation is moved before coding; candidate verification uses
those same scenarios, including consumers outside changed files.
Local probes run only in evaluator-owned immutable exports, never the live source
checkout, and require inspected helpers/no inherited external-resource authority.
Review covers cumulative fix changes, not a new whole-feature audit. Reuse unchanged
verified evidence truthfully. New source findings are verified, fixed and delta-reviewed.

Named preparation is /lite-acceptance (workflows/prepare.js); named candidate
review is /lite-review (workflows/review.js). Preparation and verification both get
explicit current-run operator grants/restrictions with source-message provenance.
Never infer a fresh child's authority from parent history or silently narrow a
permitted fixture to loopback-only. Role ceilings and later user revocations still
apply; no fixture/stand permissions are granted by the existence of a suite file.
The acceptance.py helper checks file integrity only, not truth or OS permissions. Use its exact
verified API recipe, not newly generated scripts or full tool-reference downloads.
These are native pi-subagents operations; if that recipe mismatches runtime, stop
and inspect the specific mismatch. Do not guess fields or silently self-review.
Reviewer/ops output:false + outputMode:inline: files hold short/detail evidence;
final messages are status/paths only. Format-only defects do not invalidate complete
source evidence or justify repeated source review; preserve honest provenance.

Local commits require explicit user permission; then follow shared git-workflow
and repository Git/changelog conventions (no agent co-author). The experimental
branch is an explicit exception to the production one-branch-per-ticket procedure.
Never switch/merge/reset/stash/clean another checkout. No push, remote notes, MR,
merge, deployment or source-branch updates without separate explicit permission.

Do not inherit permissions from the old session, especially shared Docker socket,
networks, firewall helper, or deletion of historical stands. Inspect test entry
points before execution. No fixed-name wiring wrapper, inherited stand DSN, shared
DB, host firewall/NET_ADMIN, Docker socket mounts or existing-resource mutation.
A private uniquely named disposable backend is allowed ONLY under actual user
approval after ownership/ports/roles are verified. Preserve split PG security roles,
goolm tags, skipped/failed/pending evidence; do not claim E2E/CI from unit results.

Keep one small result/index: request IDs, dispositions, commits, check provenance,
review links and remaining gates. For each original criterion keep source
conclusion separate from each frozen case's actual result. Requirement acceptance
and delivery readiness are DIFFERENT verdicts. Failed, skipped or blocked required
cases prevent requirement acceptance. Separately agreed delivery-only gates may
remain pending, never production acceptance. No claim that all issues are fixed
solely from source review, mock PASS or changed-path counts. Details/logs are linked files, not a growing
Frontier/history or a new state database. For comparison, local fix+review completion
is distinct from production acceptance: report remaining CI/E2E prerequisites.
Stop for the user if authority is missing, a confirmed failure repeats without a
new diagnosis, or fixing the scope requires a wider design decision. Do not turn
that blocker into an endless investigation or another phase-reset ritual.
